# Архитектура проекта

Проект разделён на независимые игровые данные, игровую логику и представление.

- `core/` — модели и логика без зависимости от конкретного UI.
- `data/` — настраиваемые Godot Resources с параметрами GDD.
- `ui/` — сцены и скрипты представления; UI получает данные через ресурсы.
- `tests/` — headless-проверки моделей, ресурсов и сцен.

Стартовая сцена — `res://ui/main/main.tscn`. Логический viewport зафиксирован как
960×540 (16:9), а интерфейс растягивается в режиме `canvas_items` с аспектом
`expand`. Основной экран заранее разделён на области поля, результата хода и боя
в пропорции 60/8/32 из GDD.

Игровые константы нельзя хранить в UI-узлах. Они задаются в
`res://data/game_rules.tres` на основе класса `GameRules`, поэтому будущие игровые
системы и headless-тесты могут использовать один источник параметров.

Модель поля находится в `core/board/`. `BoardModel` хранит состояние клеток и
предоставляет запросы к нему, а `BoardGenerator` создаёт стартовую раскладку по
весам `GameRules`. Генератор можно инициализировать seed, что делает сценарии
воспроизводимыми в тестах и будущих симуляциях баланса.

`BoardModel.find_valid_moves()` возвращает все уникальные соседние обмены,
создающие комбинацию. `BoardShuffler` используется только для поля: при тупике
он переставляет существующие камни без изменения боевого хода, сохраняет их
количество и принимает лишь раскладку без готовых совпадений и с валидным ходом.

Ввод проходит через `BoardInputController`: он одинаково обрабатывает выбор двух
клеток и начало/конец drag, проверяет соседство и умеет полностью блокироваться
на время разрешения хода. `BoardView` отвечает только за перевод координат мыши
или touch в координаты поля и визуализацию состояния модели.

`BoardTurnController` владеет транзакцией обмена. `begin_swap()` временно меняет
модель для визуального предпросмотра, а `finish_swap()` либо фиксирует валидный
ход и увеличивает счётчик, либо восстанавливает исходные клетки. Сигнал
`turn_committed` испускается только для валидного хода, поэтому будущий контроллер
боя не запустит ответ врага после отката.

`MatchFinder` сначала находит максимальные горизонтальные и вертикальные линии,
затем объединяет пересекающиеся линии одного типа в `MatchGroup`. Группа хранит
уникальные клетки и только одну, наиболее сильную форму по множителям GDD:
`5+`, затем `Т/Г`, `4` и `3`.

`BoardResolver` удаляет найденные группы, передаёт поле в `BoardCollapser` для
гравитации и дозаполнения и повторяет поиск до стабильного состояния. Каждый
`CascadeStep` хранит группы, удалённые клетки, число новых камней и множитель
каскада от ×1,00 до предельного ×2,00. Разрешение не меняет счётчик ходов.
После стабилизации основной контроллер проверяет доступные ходы и использует
`BoardShuffler`, если новые камни создали тупиковую раскладку.
